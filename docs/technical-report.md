# Technical report

E-commerce platform for the Algions AI Labs assessment: a customer store and an admin panel served from
one Next.js 16 application, routed by host name. Details of every decision are in
`docs/TECHNICAL_DECISIONS.md` (TD-001 to TD-029); limitations in `docs/REQUIREMENTS_TRACEABILITY.md`.

## Architecture

- **Modular monolith.** One deployable; business rules live in modules under `src/modules/` (identity,
  catalogue, taxonomy, grouping, inventory, cart, pricing, ordering, payment, fulfilment, returns,
  merchandising, search, reporting, audit). Route handlers stay thin: authenticate, validate once with Zod,
  call a service. Queries live only in repositories.
- **Two sites, one codebase.** The proxy maps `store.*` to `/store/*` pages and store APIs, `admin.*` to
  `/admin/*` pages and admin APIs; an admin API on the store host is a 404.
- **Data.** PostgreSQL is the only source of truth. Elasticsearch is a read model fed by a transactional
  outbox (`search_outbox`, written in the same transaction as the change); search falls back to
  PostgreSQL while Elasticsearch is down. Redis caches catalogue pages and holds rate-limit counters, and
  is never on an inventory, order, payment or coupon path.

## Correctness under concurrency

- **Multi-warehouse inventory.** Stock is per variant × warehouse with on hand, reserved and a generated
  available column; CHECK constraints keep 0 ≤ reserved ≤ on hand. Every change is a guarded
  `UPDATE … WHERE` plus a ledger row in the same transaction; rows are always locked in (variant,
  warehouse) order, and a runtime tracker enforces the documented lock hierarchy in tests.
- **Checkout.** One transaction: idempotency key + request fingerprint (same key, same body → same order;
  different body → 422), re-pricing (409 with the new breakdown), COD limit, serviceable pincode, coupon
  guarded increment, allocation (priority, or the optional nearest-PIN order) and reservation. 10 parallel checkouts for 3 units over two
  warehouses reserve exactly 3.
- **State machines.** Orders and shipments move only through typed transition tables with
  `WHERE status = <expected>`; the order status is recomputed from its shipments in the same transaction.
- **Idempotent staff stock requests.** Adjustments, receipts and transfers carry an `Idempotency-Key`;
  a replay returns the original result.

## Payments and fulfilment

- Cash on Delivery plus a **simulated online gateway** (owner decision): deterministic success and decline,
  retries, duplicate protection, every attempt persisted. No real money moves.
- Courier is the built-in `demo_courier` behind a provider interface: AWB, PDF label, HMAC-signed webhooks
  with replay protection, and an admin "simulate next scan" button. A real courier is another adapter.
- Returns and exchanges: request within the window (delivered units only), approve or reject, pickup,
  receive, restock, then a manual refund reference (capped at what was paid) or a free replacement order.

## Security

Argon2id passwords; opaque session tokens stored as SHA-256 hashes; role-based permissions loaded per
request; same-origin check on every mutation; DB-backed rate limits on sign-in, OTP, registration,
checkout and inventory writes; CSP without third-party scripts; every money, stock, order and staff
change audited with actor, before and after (never secrets).

## Trade-offs

- A monolith with module boundaries instead of services: simpler transactions and tests; modules could be
  split later along their repositories.
- PostgreSQL row locks and guarded updates instead of distributed locks: correct and testable at this
  scale; throughput under heavy contention is not measured (L41, L43).
- Search consistency is eventual (outbox), while stock checks at checkout always read PostgreSQL.
- CSV, PDFs and OpenAPI are generated by small in-repo code rather than libraries, except Swagger UI.

## Limitations (summary)

Not deployed (local only); GitHub Actions CI passing on `d144a2f` (reported by the owner); COD and a simulated gateway only (the
simulation is off in production); one simulated courier; allocation is priority-based by default, and the
optional "nearest" strategy approximates distance by shared PIN prefix (no coordinates dataset, TD-030);
notifications are simulated (audit-log rows, no sending, so no failure history); whole-order cancellation
only; manual refunds; OTP shown in a demo popup instead of SMS (never in production). The full
register, with where each item would be addressed, is in `docs/REQUIREMENTS_TRACEABILITY.md`.
